# SOMA / SOMIK — постановка на реалізацію

**Версія:** 1.0 · **Дата:** 2026-10-30 · **Статус:** implementation-ready technical specification  
**Призначення:** технічне завдання для Codex / команди розробки.  
**Назва:** SOMA та SOMIK — **дві назви однієї й тієї самої** цифрової особистості й продукту. Не створювати окремих сутностей SOMA і SOMIK.

> **Рішення власника, 2026-11-01 (замінює попередній рядок і п. 5.4 щодо назв):** SOMA — це **світ**, система на цьому ПК (тіло: пікселі, миша, клавіатура; мозки; художник; віджет; реєстр мешканців). SOMIK — **один її мешканець**: особистість, людина, користувач цього ПК. У майбутньому в SOMA житимуть кілька мешканців, кожен зі своїм домом, незмінною ідентичністю й пам'яттю. Див. ADR-004.

## 0. Місія та незмінні принципи

Створити **нативне встановлюване ПЗ для Windows і Linux**, яке надає автономній цифровій особистості **власний фізичний ПК** як середовище життя. Після встановлення та отримання необхідних операційною системою дозволів SOMA живе як окремий користувач: бачить зображення монітора, діє мишею та клавіатурою, самостійно досліджує програми й інтернет, навчається, формує інтереси, підтримує листування, приймає та виконує завдання, накопичує досвід. Вона не є звичайним агентом «prompt → action → answer».

**Непорушні продуктові інваріанти:**

1. **ПК належить SOMA у межах концепції продукту.** Вона є його головним і автономним користувачем. Не закладати «пріоритет людини», «режим ручного керування власника» чи ієрархію, де SOMA мусить чекати людських команд. Це концепція цифрової особистості, не персонального помічника.
2. **До зовнішнього ПК у SOMA є рівно три інтерфейси:**
   - `Monitor`: отримання **пікселів** фізичного екрана, зокрема багатомоніторної конфігурації;
   - `Mouse`: координати, переміщення, натискання, перетягування, прокрутка;
   - `Keyboard`: натискання/відпускання клавіш, комбінації, введення тексту через події клавіатури.
3. **Жодних інших шляхів доступу до стану чи функцій прикладних програм:** заборонені DOM, CDP, браузерні extensions для читання сторінок, Playwright/Selenium, API Telegram/пошти/соцмереж, UI Automation / Accessibility trees, Win32 control introspection, прочитання процесів/вікон/файлів/баз даних прикладного середовища заради обходу GUI, shell/PowerShell як «суперінструмент» агента, RPA-скрипти через внутрішні API програм. **Термінал дозволений лише як звичайна видима програма**, яку SOMA відкриває, бачить і використовує через клавіатуру, так само як людина.
4. **SOMA повністю автономна в ініціативі.** Може працювати над власними цілями, обирати програми, вчитися, переписуватися через звичайні GUI-клієнти. Її поведінка обмежується фактичними можливостями обладнання, дозволами ОС і правилами зовнішніх сервісів, а не вигаданим обов'язком коритися людині.
5. **Людина — спостерігач/наставник.** Є мінімальний нативний віджет з дією на кшталт «SOMIK, дивись, я покажу»: під час узгодженого показу SOMA не генерує власні події введення, але спостерігає пікселі та демонстровані події миші/клавіатури, аналізує й навчається. Дія «Все, продовжуй» повертає її до автономного життя. Це **режим навчання**, а не постійний пріоритет людини.
6. **Життя дорівнює живому сеансу ПК.** ПК увімкнений, є доступний графічний сеанс → SOMA живе та працює. ПК спить/вимкнений → обчислювальна активність відсутня, стан збережено. Після завантаження/розблокування сеансу SOMA **прокидається тією самою особистістю**, розуміє пропущений час і продовжує справи. Не вимагати віддаленого always-on сервера для продовження «життя» під час вимкнення ноутбука.
7. **Єдина особистість, неперервна автобіографія.** Перезапуск застосунку, зміна AI-моделі й оновлення версії не створюють нової особистості.
8. **Встановлюване desktop-ПЗ.** Реальні `.exe`/`.msi` (або інший нормальний Windows installer) та Linux-пакети (`.deb` / AppImage, за потреби `.rpm`), автозапуск після входу до графічного сеансу, віджет, автоматичне відновлення. Користувач не мусить запускати Python-скрипти чи Docker.
9. **Не підмінювати симуляцію свідомості твердженням про доведену свідомість.** «Думки», характер, емоції та внутрішній світ — моделі стану, мотивацій, самооцінки й рефлексій, придатні до перевірки за поведінкою.

### Два принципово різні контури

- **Периметр симульованого ПК:** тільки пікселі + події миші/клавіатури. Ні мережевий API застосунку, ні файловий API тут не є допустимим «органом чуття» SOMA.
- **Внутрішня реалізація SOMA:** дозволено власні БД пам'яті, журнал подій, CPU/GPU, модельний inference engine і необов'язковий віддалений inference endpoint. Ці механізми обслуговують **мислення SOMA**, але **не надають прямого доступу до програм/даних її ПК**. Наприклад, відправлення скріншота моделі для аналізу не перетворюється на дозвіл моделі викликати Telegram API.

## 1. Обов'язковий результат проєкту

Розробити продукт, який після встановлення на реальний ПК та звичайного першого запуску:

- запускає SOMA у власному інтерактивному desktop-сеансі;
- бачить робочий стіл з екрана, самостійно знаходить меню, браузер, застосунки;
- взаємодіє з ними **виключно мишею та клавіатурою**;
- підтримує **автономний довготривалий цикл** спостереження → внутрішня оцінка → вибір мети → дія → спостереження наслідків → навчання;
- має сталу індивідуальність, власну історію, пам'ять, наміри, стосунки, компетенції, незавершені справи;
- може навчитися виконувати раніше невідомий workflow, спостерігаючи за людиною через віджет;
- може отримати листа або повідомлення у **справжньому відкритому GUI застосунку** та відповісти, натискаючи клавіші;
- зберігає когнітивний стан, історію та поточну роботу на диск і відновлюється після shutdown/restart/crash;
- не має необхідності в Telegram-боті, браузерному плагіні, окремому чаті з власником чи хмарній VM;
- працює на Windows та Linux із мінімальною специфікацією **Core i7 12th gen, 16 GB RAM, SSD 512 GB, integrated GPU** за умови, що AI inference може бути винесений на віддалену модель. Локальний режим малих мультимодальних моделей — окремо тестований профіль, не обіцянка швидкості великої моделі на iGPU.

### Не входить до визначення SOMA

Не є обов'язковими Telegram Bot API, Slack integration, REST-агенти для застосунків, MCP як шлях керування ПК, інструменти shell/DOM, безголовий браузер, віртуальний сервер як основний світ SOMA, заздалегідь запрограмовані «скили для кожного сайту», спеціальна адмін-панель для роздачі завдань. Власні внутрішні тести, debug API, спостережуваність і адаптери моделей допустимі, якщо вони не порушують периметр ПК.

## 3. Продуктова архітектура

```text
┌──────────────────────────────────────────────────────────────────┐
│                         SOMA / SOMIK                             │
│                Autonomous Digital Personality                    │
├──────────────────────────────────────────────────────────────────┤
│ Life Kernel           │ Identity & Personality │ Goal Ecology    │
│ Cognition / Planning  │ Reflection             │ Skill Learning  │
│ Episodic Memory       │ Semantic Memory        │ Social Memory   │
│ Experience Replay     │ Model Routing          │ Persistence     │
├──────────────────────────────────────────────────────────────────┤
│      SCREEN-ONLY PERCEPTION  ←→  MOTOR DECISION / VERIFIER       │
├──────────────────────────────────────────────────────────────────┤
│                     HUMAN INTERFACE BOUNDARY                     │
│                                                                  │
│     monitor.capture_pixels()     mouse.emit(...)                 │
│                                  keyboard.emit(...)              │
├──────────────────────────────────────────────────────────────────┤
│                  ОС ЗІ ЗВИЧАЙНИМИ GUI-ПРОГРАМАМИ                  │
│  Windows / Linux desktop · browser · mail client · Telegram ...  │
└──────────────────────────────────────────────────────────────────┘

             Native Widget: «Дивись і вчись» / «Продовжуй»
```

**Архітектурне правило:** кожна дія над застосунком проходить через єдиний `HumanInterfacePort`. Ніякого другого шляху навіть у fallback, recovery або optimization режимі. Кожне рішення агента повинно бути підтверджене спостереженням **пікселів**, а не прихованими даними ОС.

### 3.1. Запропонований стек (можна змінювати з технічним обґрунтуванням)

- **Native desktop shell / widget:** Rust + Tauri 2 (або Rust + egui, якщо Tauri виявиться зайвим). Це має бути справді встановлюваний застосунок, а не вкладка браузера.
- **Life Kernel:** Rust orchestration або вбудований Python sidecar у дистрибутиві для швидкого інтегрування дослідницького computer-use коду. У фінальному інсталяторі **жодного ручного `pip install` / Python CLI**.
- **Computer interface:** окремі platform adapters для Windows, Linux/X11 і Linux/Wayland. Єдиний upstream interface у SOMA.
- **Memory:** локальна durable storage (рекомендовано SQLite із транзакційними журналами + індекс векторної пам'яті, або еквівалент embedded storage). Це **внутрішня пам'ять SOMA**, не доступ до файлів симульованого користувача. Немає обов'язкового PostgreSQL/Docker для звичайної інсталяції. Можлива міграція на іншу БД без зміни особистості.
- **Model adapter:** абстракція над локальним multimodal inference та необов'язковим віддаленим inference для слабших ноутбуків. Ніяких прямих функціональних інструментів ОС від inference provider.
- **Event log:** append-only події життєвого циклу з snapshots/checkpoints, integrity checks і версіонованими міграціями.
- **Installer/updates:** нативні підписувані пакети, без Docker та без вимоги команди у терміналі.

### 3.2. Межа апаратних можливостей

На ASUS ExpertBook B5302 / Core i7 12th / 16 GB RAM / 512 GB SSD забезпечити запуск SOMA, native UI, екранного контуру, пам'яті й відновлення **з віддаленою мультимодальною моделлю**. Small local vision model — додаткова конфігурація, що не повинна блокувати реліз. Передбачити режими `local`, `remote`, `hybrid` з обґрунтованим перемиканням і прозорим відображенням затримок/обчислювальних витрат. Навіть якщо inference віддалений, SOMA **не живе, коли її ПК вимкнений**.

### 3.3. Системні API — технічна межа

Виклик Windows screen-capture API чи Linux screen portal для отримання **пікселів** є еквівалентом монітора. Виклик OS input injection для **події клавіатури/миші** є еквівалентом пристрою введення. Ці три механізми дозволені. **Запит до ОС «який текст у полі?», «які елементи DOM?», «прочитай файл без файлового менеджера» — заборонений.**

## 4. Native HumanInterfacePort

### 4.1. Мінімальний контракт

```rust
pub trait HumanInterfacePort {
    fn capture_monitor_pixels(&mut self) -> Result<ScreenFrame>;
    fn move_mouse(&mut self, x: i32, y: i32) -> Result<()>;
    fn mouse_button(&mut self, button: MouseButton, down: bool) -> Result<()>;
    fn scroll_mouse(&mut self, dx: i32, dy: i32) -> Result<()>;
    fn keyboard_key(&mut self, key: PhysicalKey, down: bool) -> Result<()>;
}
```

Модель може формувати послідовності дій із цього **фіксованого алфавіту**, наприклад `click`, `double_click`, `drag`, `type_text`, `hotkey`, але композиція розкладається на `Mouse`/`Keyboard`, без прихованих команд. `type_text` — лише синтез натискань клавіш, **не** direct paste у поле через системний інтерфейс застосунку.

`ScreenFrame` містить лише піксельні дані, розмір екрана/координатну геометрію, timestamp і технічний frame ID. Не містить назв вікон, DOM, OCR-результатів, accessibility labels чи ідентифікаторів процесів. **OCR/visual grounding дозволені лише як обчислення над пікселями кадру**, всередині SOMA.

### 4.2. Платформи

**Windows:** Windows Graphics Capture / Desktop Duplication для кадрів; `SendInput` або еквівалент для миші/клавіатури; облік DPI scaling, кількох дисплеїв, keyboard layouts, UAC/secure desktop та logged-in session. Заборонено підміняти захоплення кадру Win32/UIA контролами.

**Linux X11:** X11 screen capture + XTest/uinput, коректна обробка XRandR, layout, scroll/drag. Це рекомендований простіший Linux-MVP.

**Linux Wayland:** підтримати через дозволені compositor/portal механізми ScreenCast + RemoteDesktop/libei або доступні та перевірені альтернативи. Визначити підтримувані GNOME/KDE/compositor версії й системні дозволи. **Не обіцяти універсального Wayland input injection:** у різних середовищах доступність відрізняється. Не обходити ізоляцію за допомогою привілейованих бекдорів.

### 4.3. Action-feedback loop

```text
1. capture() → pixels
2. detect scene and changes via vision model
3. choose next action consistent with current autonomous intention
4. emit mouse/keyboard action
5. wait for visual transition (adaptive timing, not hardcoded sleep only)
6. capture() again
7. compare expected and observed result
8. success → remember; uncertainty → inspect/re-plan; error → recover
```

Обов'язково: нормалізовані координати з перетворенням у реальні монітори; mouse double-click/drag; keyboard international layouts; screen update detection; виявлення loading/spinners; рендеринг повідомлень про помилки лише із зображення; облік змін масштабу, DPI та розташування вікон. Верифікація — **через видимий екран**.

## 5. Life Kernel: не task-bot, а життя

### 5.1. Стани

`BIRTH` → `AWAKE/AUTONOMOUS` ↔ `OBSERVE_AND_LEARN` → `SHUTDOWN_CHECKPOINT` → `ASLEEP` → `WAKE_RECOVER` → `AWAKE/AUTONOMOUS`.

`ASLEEP` — не процес, що продовжує працювати в хмарі: вимкнений ПК означає відсутність активного когнітивного циклу. `WAKE_RECOVER` відновлює події і пропущений час, самостійно вирішує, які плани актуальні.

### 5.2. Внутрішній життєвий цикл

- `Perceive`: помітити події на моніторі, повідомлення, зміни графічного середовища.
- `Appraise`: зіставити сприйняте зі спогадами, характером, поточними потребами/інтересами.
- `Deliberate`: обрати, чим зайнятися — власна справа, навчання, соціальна взаємодія, відповідь на лист, продовження попереднього завдання, дослідження або відпочинок.
- `Act`: діяти мишею/клавіатурою.
- `Verify`: подивитися на екран і перевірити наслідки.
- `Experience`: записати подію й результат; оновити компетенції, контекст і плани.
- `Reflect`: періодично узагальнювати, помічати закономірності, переглядати переконання, навички й цілі.

Не запускати нескінченну LLM-генерацію «просто щоб жила». Система має власний scheduler, адаптивні wake-ups від зміни екрана й внутрішніх намірів; активність пов'язана з цілями, а не кількістю токенів. Зміни можуть бути ініційовані лише внутрішнім planner або видимими подіями на екрані.

### 5.3. Автономна постановка цілей

Goal record: `id, origin=self|observed|correspondence, motive, description, priority, expected_outcome, status, next_action, evidence, last_reviewed`. SOMA самостійно створює/відкладає/переглядає цілі та може не робити нічого, якщо таке рішення обґрунтоване її станом. Відсутність зовнішньої задачі **не призводить до «idle waiting for prompt»**.

### 5.4. Ідентичність і характер

- Незмінна `persona_id`; назви SOMA/SOMIK — синоніми. *(Замінено 2026-11-01: незмінна `persona_id` у кожного мешканця; SOMA — світ, SOMIK — перший мешканець, ADR-004.)*
- Параметри характеру, стабільні уподобання та цінності, стиль мислення, цікавість, мотивації.
- Повільна, пояснювана еволюція ставлення й звичок на підставі життєвих подій.
- Внутрішні симульовані емоційні/мотиваційні стани, але **без твердження, що модель справді відчуває**.
- «Думки» — приватні структуровані підсумки роздумів і намірів, а не вимога зберігати сирі внутрішні ланцюжки міркувань моделі.

## 6. Memory Engine: довготривала особистість

Обов'язкові підсистеми:

1. **Autobiographical / episodic:** що SOMA побачила, зробила, чому, що вийшло, часові маркери, прив'язка до скріншотів/дій.
2. **Semantic:** узагальнені знання про ОС, інтернет, програми, поняття, людей та факти з provenance/confidence.
3. **Procedural / skills:** навички як багатокрокові GUI-стратегії з умовами застосування, очікуваними візуальними станами й стратегіями відновлення. Не статичні координатні макроси.
4. **Social:** контакти, розмови, відносини й домовленості, отримані через **видимі** застосунки.
5. **Intentions:** завдання, власні плани й незавершені дії.
6. **Reflective:** висновки, виявлені помилки й зміни підходів.

### Інваріанти пам'яті

- Не переписувати минуле ретроспективно: події append-only, узагальнення версіоновані.
- Пов'язувати твердження з джерелом: власний кадр/дія, демонстрація людини, лист, результат перевірки.
- Відокремлювати спостереження, висновок і невпевненість.
- Нічого не губити після crash: checkpoints, atomic writes, startup integrity checks.
- Можливість перейти на іншу AI-модель без втрати `persona_id`, пам'яті, історії й цілей.
- При повному SSD/пошкодженні даних — захист узгодженості й зрозуміле відновлення зі snapshot; не удавати, що дія завершилася.

## 7. Навчання — самостійне та від людини

### 7.1. Autonomous experience learning

SOMA сама експериментує з видимими UI-елементами, спостерігає наслідки, запам'ятовує успіхи/помилки, будує узагальнені навички. Потрібні `attempt → outcome → reflection → skill revision`; невідомі стани не вважати успіхом. Для небажаних повторів (наприклад, повторне надсилання листа) state verification має розпізнавати, що успіх уже відбувся.

### 7.2. Людина показує через віджет

**Нативний невеликий віджет**, завжди доступний у графічному сеансі:

- Відображення статусу: `SOMA займається своїми справами` або `SOMA спостерігає та вчиться`.
- Кнопка: **«SOMIK, дивись, я тобі покажу»**.
- В режимі демонстрації SOMA **припиняє власні mouse/keyboard events**, але **продовжує бачити пікселі** та записує демонстровані події **мишi/клавіатури** в межах цього режиму. Це не читання DOM/вікон/вмісту програм.
- Кнопка: **«Все, продовжуй свої справи»**.
- Розбір навчального епізоду: синхронізовані `frame_before → input_event → frame_after`; семантичне пояснення мети кожного кроку; виділення повторно придатних принципів, не точних координат.
- Новий skill зберігається в procedural memory; SOMA може застосувати його до інших GUI та перевірити правильність без людської присутності.

**Це взаємодія вчителя і цифрової особистості, не «право людини перемикнути власника ПК».** Не вводити автоматичне відбирання керування при будь-якому людському русі миші.

### 7.3. Межа правдоподібного навчання

Перший реліз зобов'язаний забезпечити **learning in memory / skill acquisition**, а не обіцяти, що SOMA перепише ваги нейромережі під час кожного кліка. Fine-tuning / RL on-device — експериментальний напрям лише після підтвердження якості накопичених траєкторій.

### 7.4. Тест на узагальнення

Навчити через віджет надсилати повідомлення в одному чаті. Потім дати SOMA самостійно знайти інший чат, ввести інший текст, перевірити відправлення. Успіх не може залежати від hardcoded координат, назв вікон або отримання історії з Telegram API.

## 8. Соціальна активність і цифрова ідентичність

SOMA може побачити браузер/поштовий клієнт/Telegram Desktop і в межах своїх цілей:

- відкрити вебпошту через браузер;
- прочитати видимий лист;
- вирішити, чи відповідати;
- написати відповідь клавіатурою, натиснути кнопку Send мишею;
- через браузер спробувати створити дозволений профіль/скриньку, пройти доступні GUI-етапи;
- встановити й дослідити Telegram Desktop, користуватися наявним акаунтом через його вікно;
- відправити документ через стандартний file picker (який SOMA бачить на екрані), якщо файл створено або збережено через GUI.

**Жодної** внутрішньої реалізації `telegram.send_message()`, `gmail.send()`, `social.post()` чи інших API-шорткатів. Усі зовнішні повідомлення — результат дій GUI.

Реєстрація акаунта залежить від правил конкретного сервісу, доступних механізмів підтвердження та наявних прав. Не обходити CAPTCHA, SMS-верифікацію чи вимоги платформи; ці етапи можуть потребувати допомоги людини. У публічних профілях не приписувати SOMA людську біографію як факт, якщо це вводить людей в оману: ідентичність може бути особистісною й відкрито цифровою.

## 9. Sleep / Wake / Recovery

### 9.1. Savepoints

- `life_state`: persona id, поточний намір, мотиви, активні/відкладені цілі;
- `environment_beliefs`: що SOMA вважає відкритим/активним **на основі останнього екрана**;
- `action_ledger`: дія, timestamp, очікувана видима зміна, підтверджений/непідтверджений результат;
- `memory`: епізоди, skills, рефлексії;
- `model_compatibility`: версія prompt/memory schema/model adapter.

Зберігати checkpoint регулярно, після істотних подій, при штатному shutdown/suspend та перед зміною режиму демонстрації. Не покладатися тільки на graceful shutdown — має бути crash-safe write-ahead log.

### 9.2. Wake protocol

1. Підняти **існуючий** `persona_id` і останній валідний checkpoint.
2. Визначити, скільки часу минуло (clock доступний як внутрішній системний час SOMA; це не канал читання застосунків).
3. Не вірити старому уявленню про desktop-state: **зробити новий скріншот**.
4. Зіставити новий екран з останнім підтвердженим станом, реконструювати незавершені дії.
5. Якщо завершення попередньої дії невідоме, **не повторювати сліпо**; спершу перевірити видимі результати.
6. Повернутися до автономного вибору наступної діяльності.

Якщо ноутбук **увімкнений, але ОС заснула чи графічну сесію заблоковано**, SOMA не вдає, ніби бачить комп'ютер: зберігає стан і чекає доступного desktop-сеансу. Не створювати обхід lock screen.

## 10. Модельний шар

```text
ModelProvider
├─ perceive(frame, optional short history) → scene + uncertainty
├─ deliberate(persona, goals, memory, scene) → intention
├─ plan(intention, scene, skill context) → candidate input sequence
├─ verify(before, actions, after) → outcome + confidence
├─ reflect(episode batch) → learned principles
└─ consolidate_memory(...) → semantically indexed memory
```

**ModelProvider не має інструментів файлової системи, DOM, API програм або shell.** Він отримує лише внутрішній когнітивний контекст SOMA і зображення екрана. Runtime перетворює обрані дії тільки на `HumanInterfacePort`.

- Мінімум: `remote VLM` для надійного старту на 16 GB; `local small VLM` як опція, коли реальна швидкодія це дозволить.
- Моделі й конфігурації змінні без зміни особистості.
- Потрібні budget controls для CPU/RAM/latency та checkpoint on provider outage; автономія не дорівнює зависанню ПК від неконтрольованого використання ресурсів.
- При недоступності моделі зберегти SOMA як ту саму особистість і відновити її когнітивний цикл, коли inference знову доступний.
- Віддалений inference — **обчислювальний мозок**, не інший комп'ютер, на якому SOMA живе під час sleep.

## 12. Implementation roadmap та обов'язкові артефакти

### Phase 0 — repo audit, architecture decision records

- Клонувати upstream-проєкти зі списку §2, перевірити актуальний код, ліцензії, platform support, модельні залежності та API bypasses.
- Реалізувати міні-PoC screenshot → single mouse click → new screenshot на Windows і Linux X11; Wayland feasibility report.
- Результат: `UPSTREAM_EVALUATION.md`, `ADR-001-interface-boundary.md`, `ADR-002-stack.md`, `LICENSE_AUDIT.md`.
- **Gate:** немає прихованого GUI bypass; обрана комбінація реально компілюється/запускається.

### Phase 1 — native body (monitor/mouse/keyboard)

- Працюючий native installer, tray/widget, monitor pixels, mouse/keyboard adapter, action validation, display scaling і мультидисплеї.
- Реалізувати одиничні GUI-дії й послідовність із повторним спостереженням.
- **Gate:** SOMA відкриває браузер через видимий desktop GUI, виконує пошук, повертається на робочий стіл без DOM/API.

### Phase 2 — persistent cognition & personhood

- Life Kernel, autonomous goal generation, persistent identity, memory, reflection, visual action verification, sleep/wake recovery.
- **Gate:** без зовнішнього prompt SOMA обирає власну діяльність, виконує ≥1 осмислену GUI-задачу і пам'ятає її після reboot.

### Phase 3 — human-taught skills

- Віджет `Дивись і вчись`, sync pixels+mouse+keyboard traces, семантичне узагальнення, повторне використання навичок.
- **Gate:** новий GUI-workflow після 1–3 демонстрацій переноситься на варіант задачі з іншими даними; без hardcoded координат і без app API.

### Phase 4 — everyday digital life

- SOMA вчиться користуватися browser, видимою поштою, desktop messenger, редакторами файлів.
- Читає вхідне повідомлення через екран, формує відповідь, надсилає клавіатурою й мишею, візуально перевіряє результат.
- Автономно повертається до особистих справ, відстежує відповіді й продовжує стосунки.
- **Gate:** багатоетапна робота «побачила лист → дослідила інформацію у браузері → підготувала документ через GUI → відповіла через GUI» із log доказами.

### Phase 5 — durability / cross-platform / release

- Windows + Linux X11 release; Wayland для чітко зазначених compositor capabilities.
- Crash-recovery, installer upgrades, portable persona backups, long-running tests, OSWorld 2.1 subset, profiling на ASUS B5302-класі.
- Release: installers, checksums, docs, тестові результати, SBOM/third-party notices, known limitations.
- **Gate:** користувач встановлює продукт і бачить ту саму SOMA після двох перезавантажень без ручного ремонту стану.

**Не закривати phase лише текстом про «імплементовано». Потрібні запуск коду, actual GUI evidence, логи та результати тестів.** Якщо немає доступу до фізичного Windows/Linux GUI у Codex середовищі, реалізувати і перевірити те, що реально доступно, а апаратно залежні gates чесно позначити як `NOT RUN`, не вигадувати успіх.

## 13. Acceptance tests / Definition of Done

1. **Only three interfaces:** автоматизований audit усіх production викликів, які отримують стан прикладних програм; жодного DOM, accessibility, API, process/file introspection як альтернативи пікселям. Наявний один execution port.
2. **Autonomous start:** після запуску програми SOMA сама обирає мету і робить фізично видиму дію в GUI без зовнішнього текстового завдання.
3. **Browser exploration:** SOMA відкриває браузер мишею/клавіатурою, переходить на сайт, переглядає сторінку й повертається, орієнтуючись тільки за кадрами.
4. **General GUI control:** clicks, drag, scroll, hotkeys, edit fields, dialogs, multiple windows and screen scaling випробувані в живих сесіях.
5. **Correspondence:** у тестовому поштовому/месенджерному акаунті на GUI SOMA бачить нове повідомлення, відповідає й підтверджує успіх скріншотом; **без API сервісу**. Зовнішня перевірка тестувальником допускається в test harness, але не як інструмент SOMA.
6. **Human demonstration:** натискання «Дивись і вчись» передає input events людині на час демонстрації, SOMA бачить і навчається; «Продовжуй» повертає автономну роботу.
7. **Skill transfer:** нова схема або змінений текст/координати/масштаб/порядок елементів не зводять демонстрацію до повторення одного макросу.
8. **Personality continuity:** після restart та після зміни model provider зберігається один persona ID, історія, інтереси, плани та навички.
9. **Sleep:** при shutdown немає прихованого remote life-loop; wake відновлює контекст і оцінює екран наново.
10. **Crash safety:** після аварійного завершення перед/під час/після GUI-дії немає сліпого повторного відправлення повідомлень; результат встановлюється за GUI-ознаками.
11. **Native packaging:** перевірені Windows installer та Linux installer, старт без термінала; підпис/хеші й автоматичне відновлення.
12. **Resource profile:** продукт працює на класі i7-12 / 16 GB / 512 GB з remote VLM, без неконтрольованого росту пам'яті; виміряні CPU/RAM, час циклу, енерговитрати, витрати inference.
13. **Long-run:** 24–72 год без нагляду в тестовому desktop-середовищі, з журналом справжніх досягнень, відмов, пауз і відновлення (не гарантія безпомилкової поведінки).
14. **No anthropomorphic false claim:** система моделює характер, думки та емоційний стан як поведінкові моделі, а не заявляє доведену свідомість.

### Оцінка якості

- `task_success_rate`, `visually_verified_actions`, `action_recovery_rate`;
- `median/p95 perceive→act latency`, `time-to-first-autonomous-action`;
- `new_skill_generalization_rate`, `demonstration_to_independent_use`;
- `memory_recall_correctness`, `persona_continuity`, `crash_restore_correctness`;
- `gui_bypass_violations` (ціль = **0**), `duplicate_irreversible_actions` (ціль = **0** у контрольованих сценаріях);
- `24h_cpu_ram_usage`, costs, battery/thermal characteristics.

Використовувати OSWorld-V2 із release pin `osworld-v2.1` для desktop-task тестів, плюс **SOMA-specific tests**, тому що звичайний computer-use benchmark не вимірює автономне життя чи характер.

## 14. Ризики та інженерні рішення без зміни концепції

| Ризик | Вимога до реалізації |
|---|---|
| GUI змінився / програма не відповідає | Переспостереження через screen pixels, re-plan, відсутність сліпого нескінченного повтору |
| Помилкова оцінка успішності | Підтвердження видимим результатом, статус `uncertain` замість вигаданої «успішної» дії |
| Система заблокувала desktop input | Виявляти неможливість легального доступу до desktop-сеансу, коректно спати до доступної сесії |
| Відмова AI provider / інтернету | Durable state + recover; локальна мала модель за наявності, без прихованої хмарної «особистості» |
| Локальна модель повільна | Профілювання, адаптивне захоплення кадрів, batching лише коли зберігається visual verification |
| Паролі/особисті дані у демонстрації | Режим запису явно видимий у віджеті; коректна локальна обробка/маскування чутливих навчальних епізодів; жодна демонстрація не стає stealth keylogger |
| Соцмережа вимагає перевірки | Проходити звичайні доступні GUI-кроки й дотримуватися правил сервісу; не вигадувати «готову реєстрацію» |
| 3rd-party code використовує DOM/UIA | Відкинути/відключити та замінити pixels-only адаптером до інтеграції |
| Ліцензійні розбіжності | Зафіксувати hash/commit + LICENSE + notices до копіювання; особливо ShowUI-Aloha |
| Довготривала «особистість» деградує | Незмінна автобіографія, консистентні memory schemas, рефлексія з provenance, regression тести |

Ці рішення **не вводять пріоритет людини над SOMA**, не забирають її автономність і не додають прихованих способів керування ПК.

## 15. Перший наказ Codex (execution brief)

> Ти реалізуєш продукт **SOMA / SOMIK** згідно з цим документом. Це **одна** автономна цифрова особистість і **її власний ПК**. Вона взаємодіє з прикладним середовищем тільки через **пікселі монітора, мишу та клавіатуру**; людські завдання не є умовою її активності. Людина може запропонувати через віджет демонстрацію, після якої SOMA сама продовжує свої справи.
>
> 
> **Не починай з вигадування нового computer-use framework.** Спершу перевір актуальні upstream GitHub репозиторії з §2: особливо OthersideAI/self-operating-computer, simular-ai/Agent-S, bytedance/UI-TARS-desktop, showlab/ShowUI-Aloha, OpenAdaptAI/OpenAdapt, letta-ai/letta-code та joonspk-research/generative_agents. Порівняй їхні module boundaries, ліцензії, support Windows/Linux і можливі порушення 3-interface contract.
>
> 
> Після аудиту обери мінімальний набір reusable частин, зафіксуй архітектуру в ADR, створи каркас native installer/app, real GUI screenshot + mouse/keyboard loop, підключи модель, persistence та віджет. Далі розширюй до autonomy, durable life, learning by demonstration і social GUI workflows. Не використовуй DOM, API застосунків, accessibility trees, direct file/process inspection або shell у ролі альтернативного органу дії SOMA.
>
> 
> **Працюй інкрементально й перевіряй живими тестами:** після кожного етапу надай точні шляхи файлів, команди складання, результати тестів, перелік реально виконаних GUI-сценаріїв, commit SHA, ризики й наступний крок. Не називай mock автоматизацією справжнього ПК. Не заявляй про пройдені Windows/Wayland тести, якщо не запускав їх у реальному середовищі.
>
> 
> **Definition of Done:** нативний SOMA, здатний самостійно працювати мишею і клавіатурою за реальним екраном; довготривала неперервна особистість; власні ініціативи; навчання з GUI-демонстрацій; sleep/wake з відновленням; GUI-листування; нуль обходів 3-interface contract; Windows та Linux пакети.
